# SugarPedia: 个人知识沙盒与多维认知网络

## 项目定位

**SugarPedia** 是一个完全公开的、持续生长的网状知识库。
它既是作者的"外接大脑"和折腾工作台，也是一个纯粹的研究型沙盒，欢迎任何访客随意漫游。

这里记录庞杂的好奇心：从量子物理到计算机底层逻辑，从医学影像原理到历史人物传记，乃至古典训诂学。

原则：**知识无边界，弱目录结构，强节点链接。**

---

## 🔒 内容安全纪律

本项目托管于公开的 GitHub Pages，因此所有入库内容遵守同一条底线：**只谈客观知识与主观认知，不涉及物理实体配置。**

不出现的内容包括：

1. 网络与基础设施细节（真实 IP、域名、端口映射、SSH 配置等）
2. 具体硬件资产清单（只讨论抽象的技术原理）
3. 任何个人身份信息
4. 密钥与凭证

涉及私人环境的运行手册与配置，均在其他私有环境中管理，与本仓库物理隔离。

## 📂 仓库目录结构

因为兴趣极度庞杂，传统的"树状学科分类"注定会走进窄巷（比如"科技史"该放历史还是物理？）。因此，目录只做最粗粒度的**"文、理、工、问、录"**划分，真正的分类靠 `[[双向链接]]` 和 `tags` 来完成。

```text
sugarpedia/
│
├── content/
│   ├── index.md                 # 首页：知识库控制台与随机入口
│   │
│   ├── 01_nature/               # 🌌 自然科学 (客观世界的底层规律)
│   │   ├── physics/             # 物理学 (量子力学、热力学...)
│   │   ├── chemistry/           # 化学
│   │   └── biology/             # 生物学与医学影像 (PET, CT...)
│   │
│   ├── 02_culture/              # 🏛️ 人文社科 (人类活动的痕迹)
│   │   ├── history/             # 历史记录与推演
│   │   ├── biography/           # 人物传记 (不仅记生平，更记其思想)
│   │   └── philology/           # 训诂学、语言学、古典文献解析
│   │
│   ├── 03_engineering/          # ⚙️ 工程技术 (人类改造世界的工具)
│   │   ├── computer_science/    # 计算机科学原理、算法、架构
│   │   └── machinery/           # 机械工程、电子电路理论
│   │
│   ├── 04_questions/            # ❓ 悬赏与探究 (尚未搞懂的问题池)
│   │
│   ├── 05_workbench/            # 🛠️ 折腾记录 (脱敏后的技术实践)
│   │
│   └── 06_sources/              # 📖 溯源库 (输入来源)
│       ├── books/               # 读书笔记
│       └── papers/              # 论文解析
│
├── quartz.config.ts             # 站点全局配置
└── README.md                    # 本设计文档
```

### 归位判据（当不知道放哪时）

按顺序问四个问题：
1. **它是一个尚未解决的问题吗？** → `04_questions/`
2. **它是一个动手实践的分析记录吗？** → `05_workbench/`
3. **它是对外部输入的转述吗？** → `06_sources/`
4. 以上都不是，是纯知识 → 按对象属性选：自然的规律 → `01`，人的痕迹 → `02`，人造的工具 → `03`。

"科技史放哪"这类纠结：**放哪个都不算错，靠 tag 修正**。比如目录放 `02_culture/history/`，但打上 `history, physics` 双 tag，图谱自然把它和物理节点连起来。

## 🏷️ 命名与 Tag 规范

### 文件命名

* 一律使用**中文全称命名**（如 `正电子湮灭.md`），因为 Quartz 会用文件名生成 URL 与节点标题，中文可读性优先。
* 不用日期前缀、不用编号——顺序感交给目录名的 `01_~06_`，文件永远靠搜索和链接到达。
* 一个文件只讲一个概念。想写"量子力学"，拆成"波函数坍缩"、"贝尔不等式"等原子笔记。

### Tag 策略：受控词汇 + 自由延伸

* **受控 Tag（小写、固定）**：对应六大目录的学科域，如 `physics`、`chemistry`、`biology`、`history`、`biography`、`philology`、`cs`、`engineering`、`question`、`workbench`、`book_notes`、`paper_notes`、`stub`（占位笔记）、`milestone`（认知转折）。
* **自由 Tag（camelCase，随意生长）**：跨界组合用，如 `信息论x训诂学`、`可视化`。定期回顾，出现 3 次以上的自由 tag 升级为受控 tag。
* **每篇笔记必须有一个受控 tag**——这是图谱分区渲染的锚点。

## ✍️ 内容写作规范

### 1. 元数据 (Frontmatter) 标准

```yaml
---
title: 考据学与正则表达式的暗合
aliases: [Textual Criticism and Regex]
tags: [philology, cs, milestone]
date: 2026-09-24
status: growing   # seed(占位) / growing(生长中) / stable(稳定) / questioned(存疑待考)
up: "[[清代考据学]]"   # 可选：上位概念，只填一个最重要的
---
```

`status` 字段让"未完成"成为一种显式状态而不是愧疚来源。

### 2. 双向链接网络 (Wikilinks)

当知识极度庞杂时，**跨界链接**是本项目最大的价值所在。
* 允许天马行空的跳跃：例如在记录 `[[清代考据学]]` 时，链接到 `[[信息检索理论]]`。在写 `[[正电子湮灭]]` 时，链接到 `[[对称性破缺]]`。
* 绝不因为"现在还不懂"就停止建立链接。随时建立空文件占位（Orphan Pages），让子弹飞一会儿。
* **占位笔记的标准形态**：文件里只写一句"这是一个占位节点，等一个契机"+ tag `stub` + 日期。这样图谱上可见，未来搜索"stub"可批量收割。

### 3. 认知迭代 (Debugging Mindset)

词条的核心不是"抄维基百科"，而是记录"认知过程"。标准文章模板：

```markdown
---
title: ...
tags: [...]
date: ...
status: growing
---

## 一句话大白话
（如果能用一句话讲清楚，这篇笔记就算成功）

## 以前的盲区/误解
以前以为……

## 认知的转折点
看了《……》/ 某个契机才明白。

## 原理展开
（正经内容，想写多长写多长）

## 尚未解决的问题
- [[相关占位节点]]
```

四个区块都是可选的——**哪怕只写了"一句话大白话"也值得提交**。

### 4. 问题池工作流 (`04_questions/` 的生命周期)

```
捕获（一个问题一个文件，status: questioned）
  → 探究（笔记里追加线索、链接、假说）
  → 结案二选一：
      a) 搞懂了 → 正文迁往 01/02/03 对应目录，原文件留一行重定向链接
      b) 放弃   → 标记 status: parked，不删（"放弃的原因"也是知识）
```

## ⚙️ Quartz 4 配置要点

* **Graph View**：`depth: 1`（默认只看局部邻居，全局图留作入口页的震撼彩蛋）；开启 `localGraph` 组件。
* **组件取舍**：保留 `Backlinks`（本项目的灵魂）、`Explorer`（按目录折叠）、`Search`；关闭 `RecentNotes`。
* **`ignorePatterns`**：排除草稿目录，从构建层面保证未完成内容不被发布。
* **slug 化**：确认中文文件名的 URL 编码在 GitHub Pages 上的路由表现正常。
* **RSS/Sitemap**：开启 RSS。

## 📐 排版与渲染规范（避坑清单）

以下规则保证同一份 Markdown 在 GitHub、Quartz 和各类预览器中都正确渲染。

### 数学公式

1. **`$$` 公式块前后必须各留一个空行**。紧贴文字的 `$$` 块会被部分解析器吞进段落，导致渲染失败；连续两个 `$$` 块中间不加空行，会被合并成一行。
   ```markdown
   ❌ 结果是：
   $$E = mc^2$$
   其中 c 是光速

   ✅ 结果是：

   $$E = mc^2$$

   其中 c 是光速
   ```
2. **正文叙述中不使用行内 `$...$` 公式**。GitHub 对行内公式的渲染不可靠（紧邻中文时尤其如此，会直接显示原始代码）。替代方案：
   - 简单符号用 Unicode 字符直接写：e⁺、mᵢ、Δt、γ、177.36°；
   - 复杂表达式独立成块级 `$$...$$`，正文用文字引出；
   - 表格单元格内只用 Unicode，不用任何 `$`。
3. 多个公式各自独立成块，不要把两个结论塞进同一个 `$$`。

### 图片与矢量图

4. **配图一律用 SVG**（矢量）：无限缩放不糊、体积小、数据点精确可复现。位图仅用于照片类内容。
5. 生成类图表**必须保留生成脚本**，放在 `scripts/` 并在笔记中注明路径——图是脚本的可再生输出，不是一次性手工产物。
6. 图片统一存放在 `content/assets/<主题>/` 下，笔记中用相对路径引用（如 `../../assets/display/bias.svg`）。
7. 图内文字字号 ≥12px，标题 ≥15px——保证缩略视图下仍可读。
8. 概念对比优先画"对照图"（如：理想 vs 截断、正确 vs 错误），并列呈现比文字描述更直观。

## 🚀 维护与更新工作流

* **环境构建：** 基于 [Quartz 4](https://quartz.jzhao.xyz/)，支持强大的 Markdown 解析与知识图谱渲染。
* **本地预览：** `npx quartz build --serve`
* **发布同步：** 确认内容无隐私泄露后，执行 `npx quartz sync` 自动推送到 GitHub。
* **更新心态：** 把这里当做赛博花园，想种什么种什么。不需要追求"系统学完一门课"，只需要"随时随地捕获一个新概念"。
* **定期整理**：搜索 `status: seed` 和 `stub`，收割占位节点；回顾自由 tag 是否需要升级。
